# Hexasphere — code review

Ключевой контекст: на сцене может быть **несколько** `HexasphereNode` одновременно, и они должны работать независимо друг от друга.

---

## 🔴 Критично: независимость нескольких гексасфер на сцене

### 1. Нет арбитража input между инстансами

**Проблема.** В `HexasphereNode._UnhandledInput` для ЛКМ / СКМ / hover нигде не вызывается `GetViewport().SetInputAsHandled()`. Каждая гексасфера независимо делает свой raycast на **любое** событие мыши, не зная о существовании других планет на сцене. Если планеты перекрываются на экране (одна ближе к камере, другая дальше), клик может одновременно затронуть обе — нет сравнения "кто ближе", то есть нет z-приоритета между разными сферами.

**Решение.** Вынести обработку input в единый роутер (autoload/singleton), например `HexasphereInputRouter`:
- каждая `HexasphereNode` регистрируется в нём в `_Ready()` и отписывается в `_ExitTree()`;
- роутер на каждое событие мыши один раз проходит по всем зарегистрированным нодам, вычисляет `t` пересечения луча со сферой у каждой, находит **ближайшую** (минимальный `t`);
- только у "победителя" вызывается обработка клика/hover, остальные получают явный "мимо";
- роутер сам вызывает `SetInputAsHandled()`.

Это также решает и проблему производительности (см. п. 9 ниже).

---

### 2. Общая 3D-камера трактуется так, будто она принадлежит одной планете

**Проблема.**
```csharp
_camera3D = GetNodeOrNull<Camera3D>("../Camera3D"); // fallback
```
`OpenUvProjector()` и `OnProjectionClosed()` в каждой `HexasphereNode` напрямую включают/выключают одну и ту же 3D-камеру (`Current = true/false`, `ProcessMode`). Если несколько планет используют общую камеру:

- Планета A открывает UV-проекцию → выключает камеру.
- Планета B закрывает *свою* UV-проекцию (которая уже неактивна) → снова включает камеру, хотя оверлей A всё ещё видим на экране.

Возникает гонка состояний за общий ресурс между независимыми нодами.

**Решение.** Ввести единого владельца UV-режима/камеры — либо singleton-менеджер с явным флагом "кто сейчас держит UV-режим", либо счётчик активных UV-проекций вместо прямого `Current = true/false` из каждой ноды по отдельности.

### 3. Хардкод путей к дочерним узлам

**Проблема.** `GetNodeOrNull<UvCamera2D>("Camera2D")` — строковый путь дублируется в нескольких местах `HexasphereProjectorController`. Если иерархия сцены у конкретного инстанса чуть отличается от эталонной, получаем тихий `null` — фича молча перестаёт работать, без ошибки.

**Решение.** Завести `[Export] NodePath Camera2DPath`, резолвить и кэшировать один раз в `_Ready()`.

### 4. Потокобезопасность генерации под вопросом

**Проблема.**
```csharp
var hexasphere = new NativeHexasphere();
Task.Run(() => GenerateInBackground(hexasphere));
...
_native.Call(MethodGenerate, ...) // вызов метода на GDExtension-объекте из фонового потока
```
Комментарий в коде утверждает, что «чистая C++ генерация безопасна в фоновом потоке», но это допущение, а не гарантия. `GodotObject.Call` в общем случае не потокобезопасен, если это явно не заявлено в самом GDExtension. При нескольких гексасферах, которые генерируются параллельно (а это ваш основной сценарий), это первый кандидат на редкие крэши или повреждение памяти, если внутри C++ есть разделяемое состояние (аллокаторы, статические кэши, RNG).

**Решение.**
- Уточнить у автора GDExtension потокобезопасность/реентерабельность `NativeHexasphere`.
- Если гарантий нет — сериализовать генерацию: ограничить количество параллельных `Task.Run` семафором, либо генерировать через выделенный поток с очередью задач вместо `Task.Run` на каждый инстанс.

Дополнительно: если `GenerateInBackground` бросит исключение до `CallDeferred(FinalizePlanet)`, нативный объект `hexasphere` никогда не диспозится — утечка при каждой неудачной генерации.

### 5. Возможность одновременно открыть несколько UV-проекций

**Проблема.** Ничто не мешает открыть UV-проекцию сразу у двух и более планет — `OpenUvProjector()` не проверяет, не открыта ли уже другая проекция.

**Решение.** Если многооконный режим не задуман явно — добавить глобальный gate (например, через тот же менеджер из п. 2), который закрывает предыдущую UV-проекцию перед открытием новой, либо блокирует повторное открытие.

## 🟠 Логические баги (не связаны с мультипланетностью)

### 6. Полюсные/шовные тайлы просто выбрасываются

```csharp
if (HasPolarStretch(uvs)) continue;
```
Тайлы, задевающие полюс или линию шва (u ≈ 0/1), вообще не рисуются на 2D-карте → визуальные дыры у полюсов и по меридиану 180°.

**Решение.** Не отбрасывать такие тайлы, а корректно дублировать их геометрию: рисовать со сдвигом −1 и +1 по U по обе стороны шва, либо строить полюсный тайл отдельным веером с явной разверткой вместо усреднения по соседям.

---

### 7. `PanLimits` в `UvCamera2D` не согласован с центром карты

```csharp
camera.Position = new Vector2(mapSize.X / 2f, mapSize.Y / 2f); // например (960, 540)
...
Position = Clamp(Position, -PanLimits, PanLimits); // симметрично вокруг (0,0)
```
Лимиты паннинга заданы как константа вокруг начала координат, а не вокруг центра карты. Для карт, отличных от размера "по умолчанию", камеру можно увести далеко за пределы карты в одну сторону и почти не подвинуть в другую.

**Решение.** Вычислять лимиты паннинга динамически от `mapSize / 2 ± допустимый отступ`, а не хранить как фиксированную константу.

---

### 8. Избыточный пересчёт внутри цикла триангуляции

```csharp
for (int i = 0; i < n; i++) {
    var a = UvToScreen(uvs[0], mapSize); // не зависит от i!
    ...
}
```
`a` — общая вершина веерной триангуляции, не меняется между итерациями, но пересчитывается каждый раз.

**Решение.** Вынести расчёт `a` за пределы цикла.

## 🟢 Производительность

### 9. Raycast всех сфер на каждое движение мыши

Каждая `HexasphereNode` в `_UnhandledInput` делает полный raycast + quantize + перебор spatial bucket на **любое** `InputEventMouseMotion`, даже если мышь физически не может попасть по этой планете (не видна, за камерой, слишком далеко от текущей позиции курсора на экране).

**Решение.**
- Централизованный роутер из п. 1 сам по себе снимает часть проблемы (один проход вместо N независимых).
- Добавить дешёвый ранний отсев до дорогого raycast: например, проверка bounding sphere планеты в экранных координатах, либо грубая проверка дистанции камеры до центра планеты против её радиуса.

---

### 10. Полная пересборка 2D-меша при каждом открытии UV-проекции

`OpenUvProjector()` каждый раз вызывает `BuildMap2D`, которая заново строит всю меш-геометрию и spatial grid — даже если ни цвета, ни форма планеты не менялись с прошлого открытия. Для больших `SubDivision` (тысячи тайлов) это заметная пауза при каждом повторном открытии.

**Решение.** Кэшировать построенную меш + spatial grid между открытиями, перестраивать только по dirty-флагу при реальном изменении цветов/геометрии.

---

### 11. Фиксированный `CellSize` в spatial grid хит-теста

```csharp
private const float CellSize = 64f;
```
Не масштабируется под `MapSize` и плотность тайлов — для очень крупных или очень мелких карт сетка получается либо слишком грубой (много кандидатов на ячейку), либо слишком мелкой (лишние ячейки, лишняя память).

**Решение.** Рассчитывать `CellSize` динамически от среднего размера тайла в пикселях (например, `mapSize.Length() / sqrt(tileCount)`).

---

### 12. Аллокация нового буфера при каждом вызове `DrawColors`

```csharp
var bytes = new byte[_texWidth * _texHeight * 4];
```
Новый массив создаётся на каждый вызов, хотя размер текстуры не меняется между вызовами для одной и той же планеты.

**Решение.** Выделить буфер один раз в `InitShaderMaterial` и переиспользовать его в `DrawColors`.

## Итог

Внутри одного инстанса гексасферы код написан аккуратно: нет статических полей состояния, каждая `NativeHexasphere` / `VisualController` / `ProjectorController` честно изолирована по данным. Но **связность через input-систему и общую 3D-камеру** — то место, где несколько гексасфер на сцене сломаются в первую очередь: отсутствие арбитража "кто ближе к камере" и отсутствие единого владельца UV-режима делают поведение непредсказуемым при пересечении планет на экране. Это стоит исправить в первую очередь, до остальных оптимизаций.
